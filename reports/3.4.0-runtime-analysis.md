# BigBanana 3.4.0 Runtime Analysis

Date: 2026-08-18

This report records observations from the locally pulled `3.4.0` images. It is
intended for comparison with the public `2.0.3` source snapshot. It records
metadata, routing, bundle signatures, and behavior clues; it does not copy the
protected server bundles into this repository.

## 2.0.3 Architecture

The public `2.0.3` snapshot contains the complete editable application for
that release:

- React/TypeScript UI, routes, components, hooks, types, Vite config, and static assets.
- Client-side AI orchestration for chat, image, video, audio, prompts, script parsing, shot generation, and quality checks.
- `server/mediaProxyServer.mjs` for the media proxy.
- `server/newApiProxyCore.mjs` and `server/newApiProxyServer.mjs` for the New API account proxy.
- Dockerfiles and Nginx configuration for rebuilding the three-service stack.

It is not a self-contained SaaS backend. Project data is stored in browser
storage. `services/storageService.ts` opens `BigBananaDB` at IndexedDB version
3 and creates `projects`, `assetLibrary`, `seriesProjects`, `series`, and
`episodes` stores. Video data can be moved through OPFS and materialized when
exporting.

The model providers, the remote New API account service, and the actual model
inference systems remain external dependencies. The two Node services are
proxies and safety/routing boundaries, not the complete provider backend.

## 3.4.0 Image Evidence

### Web image

The web image runs Nginx and contains compiled output under
`/usr/share/nginx/html`. No `.ts`, `.tsx`, `.jsx`, `.mjs`, `.cjs`, or source-map
files were present in the static tree.

The principal JavaScript assets are:

- `index-D9jX3f3S.js`: approximately 6.2 MB
- `index-BhVO9P4_.js`: approximately 584 KB
- `motion-0yc2g3ly.js`: approximately 333 KB
- `novelImportService-CbCTDfPF.js`: approximately 54 KB
- `morph-transition-D7DIVyRf.js`: approximately 13 KB
- `icons-CC3OaP0_.js`: approximately 95 KB

Additional runtime assets include a PWA manifest/service worker, SEO landing
pages, showcase media, and extra responsive reference images. These are not
all core workbench code, but they show that the current frontend build is
larger and more modular than the `2.0.3` bundle.

### Nginx routes

Compared with the public `2.0.3` Nginx configuration, the `3.4.0` web image
adds these upstream routes:

| Route | Upstream | Meaning inferred from deployment |
| --- | --- | --- |
| `/api/antsk-proxy` | `new-api-proxy:8788` | Additional provider/API proxy path |
| `/api/cutos` | `cutos-api:8789` | CutOS service path |
| `/api/agent` | `cutos-api:8789` | Agent/CutOS service path |

The existing media and New API routes remain. Proxy read/send timeouts grew
from 300 seconds in `2.0.3` to 1800 seconds in the current image, and the
Nginx client body limit grew from 10 MB to 100 MB. This is consistent with
longer-running video/render jobs and larger media requests.

### Server images

The current proxy images run Node 20.20.2 and expose these protected runtime
files:

- `media-proxy.cjs`, about 12 KB
- `new-api-proxy.cjs`, about 44 KB
- `cutos-api.cjs`, about 82 KB

The files contain obfuscation-style `_0x...` identifiers. The CutOS image
history shows a build step that copies
`/app/.protected-server/cutos-api.cjs` into the runtime image. This is useful
evidence about the build boundary, but it is not equivalent to recovering the
original TypeScript source.

The CutOS image retains build metadata in `/app/package.json`. Compared with
the `2.0.3` package, the metadata adds the following relevant dependencies and
tooling:

- `dexie`: a higher-level IndexedDB layer;
- `express`: a larger server framework;
- `ffmpeg-static`: server-side media processing capability;
- `@shareai-lab/kode-sdk`: new SDK integration;
- `framer-motion`, Radix UI, `react-resizable-panels`, Markdown and i18n packages;
- `zod`: schema validation;
- `esbuild` and `javascript-obfuscator` as build tooling.

The same metadata exposes scripts named `cutos-api`, `build:server:protected`,
and a separate `studio.vite.config.mts`, which indicates a newer build and
server packaging pipeline.

## Feature Signals In The 3.4.0 Bundle

String-level inspection of the compiled bundle found identifiers associated
with features that are not represented as equivalent top-level modules in the
public `2.0.3` source:

- `NovelImportResult`, `novelToStoryboard`, and `novelPlaceholder`;
- `worldMapDraft`, `worldRules`, `worldviewAnchor`, `worldviewDraft`;
- `cutosEditor`, `cutosTimeline`, `timelineClips`, and `timelineEditedVersion`;
- `KeyframeHistory`, extended Nine Grid state, and additional render state.

These are feature and data-model signals, not a source-level diff. The bundle
is obfuscated/minified, so exact component boundaries and implementation
details still need to be confirmed through UI behavior and exported data.

## What Cannot Be Recovered From This Evidence

The following cannot be established as an exact diff without authorized
access to the `3.4.0` source delivery:

- exact changes to prompt templates and model defaults;
- exact IndexedDB/export schema migrations;
- internal CutOS API request/response contracts;
- which functions moved from the browser into `cutos-api`;
- exact UI component names and module boundaries;
- complete New API and AntSK routing behavior.

## Recommended Comparison Sequence

1. Create the same small project in ports 3005 and 3006.
2. Create one series, one episode, one character, one scene, one prop, one shot, and one generated/test media reference in each version.
3. Export the project backup from both versions and compare store names, schema version, object keys, prompt fields, model fields, media references, and timeline fields.
4. Test novel import, worldview editing, CutOS timeline operations, and batch asset completion separately.
5. Record the browser requests made by each action and map them to the old public source functions.
6. Implement only confirmed data-model and API changes in the `2.0.3` branch, keeping the old baseline runnable after each change.

The two local ports are different browser origins, so their IndexedDB and
LocalStorage are isolated. Keep backups from both versions before testing any
import or migration behavior.
